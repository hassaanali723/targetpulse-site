Ein Bounce mit 550 5.7.1 bedeutet, dass der empfangende Server Ihre Nachricht geprüft und abgelehnt hat. Der Grund ist meist eine Sicherheits- oder Richtlinienregel. Es bedeutet nicht, dass die E-Mail-Adresse tot oder gelöscht ist. Meistens ist das Postfach in Ordnung. Das Problem ist, dass derselbe Code sehr verschiedene Ursachen abdeckt. Das reicht von einem fehlenden SPF-Eintrag bis zu einer Verteilerliste, die nur interne E-Mails annimmt. Der Code allein sagt Ihnen also nicht, was Sie beheben müssen. Das sagt Ihnen die Textzeile danach, zusammen mit dem Namen des Servers, der den Bounce gesendet hat.

## Lesen Sie zuerst drei Dinge in Ihrem Bounce

Öffnen Sie den vollständigen Bounce, nicht nur die Zusammenfassung in Ihrer E-Mail-Plattform. Sie suchen den Code, den Server, der die Nachricht abgewiesen hat, und den Text nach dem Code.

Eine Ablehnung von Gmail sieht im rohen Bounce so aus:

```text
Remote-MTA: dns; gmail-smtp-in.l.google.com
Diagnostic-Code: smtp; 550-5.7.1 [203.0.113.10] Our system has detected that this message is likely unsolicited mail. To reduce the amount of spam sent to Gmail, this message has been blocked. - gsmtp
```

In diesem Auszug steht der antwortende Server in der Zeile Remote-MTA: `gmail-smtp-in.l.google.com`. Der Code steht in der Zeile Diagnostic-Code als `550-5.7.1`. Der Text nach der IP sagt, dass die Filter von Gmail die Nachricht für Spam gehalten haben. Die Zeichenfolge `- gsmtp` am Ende bestätigt, dass Gmail den Bounce erzeugt hat. Sehen Sie stattdessen die Markierung `gcdp`, etwa in `550 5.7.1 This message violates example.com email policy. - gcdp <sessionid> - gsmtp`, dann stammt die Ablehnung von einer Regel, die der Google-Workspace-Administrator des Empfängers angelegt hat.

Derselbe Code von Outlook.com liest sich ganz anders:

```text
Remote-MTA: dns; outlook-com.olc.protection.outlook.com
Diagnostic-Code: smtp; 550 5.7.1 Unfortunately, messages from [203.0.113.10] weren't sent. Please contact your Internet service provider since part of their network is on our block list (S3150).
```

Endet der Host auf protection.outlook.com, haben die Server von Microsoft die Nachricht abgelehnt. Namen wie outlook-com.olc.protection.outlook.com gehören zu den Privatkonten von Outlook.com und Hotmail, nicht zur Microsoft-365-Umgebung eines Unternehmens. Der Code ist derselbe wie im Gmail-Beispiel, aber die Ursache ist eine ganz andere. S3150 bedeutet, dass die IP, von der Sie gesendet haben, oder ein Teil ihres Netzes auf der Sperrliste von Microsoft steht. Mit der Adresse des Empfängers hat das nichts zu tun.

## Finden Sie Ihre genaue 550-5.7.1-Meldung

Jedes Mailsystem formuliert seinen 550 5.7.1 anders. Suchen Sie den Text aus Ihrem Bounce in einer der Zeilen unten.

| Text im Bounce | Gesendet von | Was er bedeutet | Wer es beheben kann |
|---|---|---|---|
| Our system has detected that this message is likely unsolicited mail. To reduce the amount of spam sent to Gmail, this message has been blocked. - gsmtp | Gmail | Spamfilter haben die Nachricht wegen der Absenderreputation, plötzlich hoher Mengen oder Beschwerden von Nutzern gesperrt | Absender |
| This message violates example.com email policy. - gcdp <sessionid> - gsmtp | Google Workspace | Ein Workspace-Administrator hat eine eigene Routing-Regel, einen Compliance-Filter oder eine Anhangsrichtlinie angelegt, die die Nachricht gesperrt hat | Administrator des Empfängers |
| Invalid credentials for relay [IP]. | Google Workspace | Die sendende Anwendung wollte den SMTP-Relay-Dienst von Google Workspace ohne gültige Zugangsdaten nutzen | Absender |
| Daily SMTP relay sending limit exceeded for this customer. | Google Workspace | Das Workspace-Konto hat sein tägliches Limit für ausgehendes Relay erreicht | Absender |
| Unfortunately, messages from [IP] weren't sent. Please contact your Internet service provider since part of their network is on our block list (S3150). | Outlook.com | Microsoft hat die sendende IP-Adresse oder den Netzbereich auf seine Sperrliste für Privatkonten gesetzt | Absender oder Internetanbieter |
| Unable to relay | Exchange und viele andere Server | Der Server hat die Weiterleitung abgelehnt, weil die SMTP-Authentifizierung fehlte oder ein Connector falsch eingerichtet war | Absender oder Administrator des Absenders |
| Delivery not authorized, message refused | Verschiedene Mailserver | Der empfangende Server hat die Nachricht nach einer internen Richtlinie abgelehnt und keine weiteren Angaben gemacht | Absender oder Administrator des Empfängers |
| Relaying denied | Verschiedene Mailserver | Der Server leitet keine Nachrichten von Dritten weiter, wenn sich der Client nicht zuerst authentifiziert | Absender |

Die ungenaueste Variante ist der reine Wortlaut aus RFC 3463, 550 5.7.1 Delivery not authorized, message refused, ohne weiteren Text. Manche Server halten den Grund absichtlich kurz, damit Spammer nicht erfahren, was den Filter ausgelöst hat. Wenn Sie über ein Relay oder einen Smarthost senden, prüfen Sie zuerst, ob sich Ihre Anwendung vor dem Senden wirklich anmeldet (SMTP AUTH). Eine Verbindung ohne Authentifizierung ist eine häufige Ursache auf Ihrer Seite. Meldet sich die Anwendung an, bitten Sie den Empfänger, die Nachricht in seinen eigenen Mail-Protokollen zu suchen. Dort ist der echte Grund meist als Einziges festgehalten.

## Wenn das Problem auf Ihrer Seite liegt

Zeigt der Bounce auf Authentifizierung, Reputation oder Relay, können Sie das Problem ohne den Empfänger beheben. Prüfen Sie zuerst die Authentifizierung. Eine Verbesserung der Reputation hilft nicht, solange SPF oder DKIM fehlschlagen.

Gmail und Outlook.com lehnen inzwischen viele E-Mails ohne Authentifizierung direkt ab. Beginnen Sie also mit dem DNS. Ihre Absenderdomain braucht [SPF-, DKIM- und DMARC-Einträge](/blog/spf-dkim-dmarc-explained). DKIM ist oft ein CNAME, den Ihr E-Mail-Anbieter Ihnen gibt. Prüfen Sie zuerst den [SPF-Eintrag](/glossary/spf). Er muss jede Server-IP und jeden Versanddienst nennen, der in Ihrem Namen Nachrichten sendet. RFC 7208 erlaubt pro Domain einen SPF-Eintrag und zehn DNS-Abfragen. Mehrere Einträge oder mehr als zehn Abfragen führen automatisch zu einem PermError. Senden Sie sich dann eine Testnachricht und öffnen Sie die Header. Die Ansicht "Original anzeigen" in Gmail listet SPF, DKIM und DMARC als PASS oder FAIL auf. Das geht schneller, als DNS-Einträge zu lesen. Der DMARC-Eintrag liegt unter _dmarc.yourdomain.com. Die Domain in Ihrer From-Adresse muss zu der Domain passen, die SPF oder DKIM bestanden hat.

Besteht die Authentifizierung und Gmail meldet trotzdem "likely unsolicited mail" (wahrscheinlich unerwünschte E-Mail), liegt das Problem meist bei der Reputation. Gemeint ist, wie Empfänger auf Ihre früheren E-Mails reagiert haben. Die [Google Postmaster Tools](/glossary/postmaster-tools) zeigen Ihre Spam-Rate. Google bittet Absender, sie unter 0,1 % zu halten und nie 0,3 % erreichen zu lassen. Steigt sie, pausieren Sie die Kampagne, statt mehr Volumen zu senden. E-Mails, die im Spam-Ordner gelandet sind, bouncen oft direkt, wenn die Reputation weiter sinkt.

Die Qualität der Liste wirkt sich direkt darauf aus. Alte Listen sind voller verlassener Postfächer. Manche Anbieter machen lange tote Adressen zu [Spam-Traps](/glossary/spam-trap). Treffen Sie diese, oder bouncen Sie an vielen Adressen, die nicht mehr existieren, sehen die Filter, dass Sie Ihre Liste nicht sauber halten. Ist die Liste älter als ein paar Monate, oder stammt sie aus Scraping oder einem Kauf, [prüfen Sie die Liste vor dem Versand](/email-list-cleaning) (auf Englisch).

Relay-Fehler sind ein eigenes Problem. Unable to relay oder Invalid credentials for relay [IP] bedeutet, dass der Server, über den Sie senden, Ihre Anwendung nicht als berechtigt erkennt.

Wenn Sie Nachrichten über den SMTP-Relay-Dienst von Google Workspace leiten, öffnen Sie die Google Admin-Konsole. Gehen Sie zu Apps, wählen Sie Google Workspace, öffnen Sie Gmail und dann Routing. Prüfen Sie die Konfiguration des SMTP-Relay-Dienstes. Authentifizieren Sie sich über die IP-Adresse, prüfen Sie, ob Ihre Server-IP in der Liste der erlaubten Adressen steht. Authentifizieren Sie sich mit Zugangsdaten, prüfen Sie, ob Ihre Anwendung über Port 587 mit TLS und den richtigen Kontodaten verbindet. Wenn Sie über Microsoft 365 senden, öffnen Sie das Exchange Admin Center und prüfen Sie Ihre Connectors unter Nachrichtenfluss. Anwendungen und Geräte, die über Microsoft 365 senden, etwa ein CRM oder ein Büroscanner, laufen meist über einen Connector. Eine falsche IP-Adresse oder ein falscher Zertifikatsname an diesem Connector ist eine häufige Ursache für 550 5.7.1 Unable to relay.

## Wenn nur der Empfänger es beheben kann

Manchmal ist die Sperre gewollt. Unternehmen mit Microsoft 365 oder Google Workspace legen oft Regeln an, die externe Absender von bestimmten Adressen fernhalten.

Ein häufiges Beispiel ist eine Verteilerliste wie all-staff@, die nur E-Mails aus dem eigenen Unternehmen annimmt. Schreiben Sie von außen an sie, antwortet Exchange Online mit einem Bounce 550 5.7.1, oft mit dem Namen der Gruppe. Die eigene Fehlerbehebungsseite von Microsoft sagt, dass der Absender das in der Regel nicht beheben kann. Der Besitzer der Gruppe oder ein Exchange-Administrator muss die Gruppe im Microsoft 365 Admin Center bearbeiten und Ihre Adresse zur Liste der erlaubten Absender hinzufügen.

Google Workspace funktioniert genauso. Die Zeichenfolge `gcdp` in einem Gmail-Bounce bedeutet, dass ein Administrator in der Google Admin-Konsole eine eigene Regel angelegt hat. Diese Regel hat Ihre Nachricht wegen des Inhalts, der Anhänge oder der Absenderdomain abgelehnt. Nichts, was Sie auf Ihrer Seite ändern, kommt daran vorbei.

Bitten Sie in diesem Fall den Empfänger, den Bounce an sein IT-Team weiterzugeben. Nennen Sie die Absenderadresse, die Empfängeradresse, die Uhrzeit des Bounces und den vollständigen Bounce, zum Beispiel so:

```text
Hallo [Name], eine E-Mail, die ich Ihnen am [Datum] um [Uhrzeit] gesendet habe, kam mit einem Richtlinienfehler 550 5.7.1 zurück. Offenbar hat eine Regel in Ihrem Mailsystem sie gesperrt. Könnten Sie die Angaben zum Bounce unten an Ihr IT-Team weitergeben, damit es die Zustellung von meiner Adresse erlaubt?
Absender: [Ihre E-Mail-Adresse]
Empfänger: [E-Mail-Adresse des Empfängers]
Diagnose: [Zeile Diagnostic-Code einfügen]
```

## Codes, die Sie neben 550 5.7.1 sehen können

Das sind die SMTP-Fehlercodes, die am häufigsten im selben Bounce-Bericht auftauchen. Manche bedeuten, dass die Adresse weg ist. Andere bedeuten, dass die Adresse in Ordnung ist und Ihre Einrichtung Arbeit braucht.

| Code | Meist von | Was er bedeutet | Was Sie zuerst tun sollten |
|---|---|---|---|
| 550 5.1.1 | Gmail, Microsoft, die meisten Server | Das Postfach des Empfängers existiert auf dem Zielserver nicht | Die ungültige Adresse dauerhaft von Ihrer Liste entfernen |
| 550 5.4.1 | Microsoft 365 | Die Empfängeradresse wurde durch Directory-Based Edge Blocking abgelehnt | Prüfen, ob der Empfänger noch bei dem Unternehmen arbeitet |
| 550 5.7.25 | Gmail | Die sendende IP-Adresse hat keinen gültigen Reverse-DNS-Eintrag (PTR) | Bei Ihrem Hosting-Anbieter einen PTR-Eintrag einrichten, der zu Ihrem Hostnamen passt |
| 550 5.7.26 | Gmail | Die Nachricht hat die Authentifizierung über SPF oder DMARC nicht bestanden | Die Syntax des SPF-Eintrags korrigieren und die DKIM-Signaturdomains abgleichen |
| 550 5.7.27 | Gmail | Ihre Nachricht hat SPF nicht bestanden | Die IP-Adresse Ihres ausgehenden Servers in den SPF-Eintrag Ihrer Domain aufnehmen |
| 550 5.7.28 | Gmail | Von der sendenden IP kam ungewöhnlich viel unerwünschte E-Mail | Langsamer senden und die Spam-Beschwerden der Nutzer prüfen |
| 550 5.7.515 | Outlook.com | Einer Domain mit hohem Volumen fehlen die nötigen SPF-, DKIM- oder DMARC-Einträge | SPF und DKIM abgleichen und einen gültigen DMARC-Eintrag veröffentlichen |

Wie sich vorübergehende und dauerhafte Bounces allgemein unterscheiden, erklärt unser Leitfaden zu [Hard Bounce vs. Soft Bounce](/blog/hard-bounce-vs-soft-bounce). In der Praxis entfernen Sie eine Adresse nach einem 550 5.1.1. Nach einem 550 5.7.26 behalten Sie sie, denn dort ist die Adresse in Ordnung und Ihre Authentifizierung ist fehlgeschlagen.

550 5.7.515 betrifft nur größere Absender. Seit dem 5. Mai 2025 lehnt Microsoft E-Mails von Domains ab, die täglich 5.000 oder mehr Nachrichten an Adressen bei Outlook.com, Hotmail und Live senden. Das gilt, wenn nicht SPF besteht, DKIM besteht und ein DMARC-Eintrag (p=none reicht) mit einem der beiden übereinstimmt.

Im Internet steht der Code manchmal als 5.7.15. Das ist aber ein anderer Code (Priorität zu niedrig). Im Bounce von Microsoft steht 5.7.515.

## Häufige Fragen

**Wie behebe ich den Fehlercode 550 5.7.1?**
Lesen Sie die Diagnosezeile in Ihrem Bounce. Sie zeigt, ob die Authentifizierung, die Reputation oder eine Regel auf der Seite des Empfängers den Fehler verursacht hat. Ist die Authentifizierung fehlgeschlagen, aktualisieren Sie Ihre SPF-, DKIM- und DMARC-Einträge und prüfen Sie Ihre SMTP-Zugangsdaten für den Versand. Hat eine Regel des Empfänger-Administrators oder eine beschränkte Gruppe die Sperre verursacht, senden Sie die Bounce-Header an den Empfänger. Dann kann sein IT-Team Ihre Adresse erlauben.

**Was bedeutet 550 5.7.1 unsolicited mail?**
Gmail sagt damit, dass seine Filter Ihre Nachricht für Spam halten. Das beruht vor allem auf Ihrer Absenderreputation. Die üblichen Ursachen sind Empfänger, die Ihre E-Mails als Spam markieren, ein plötzlicher Anstieg des Volumens von einer neuen Domain oder IP, oder der Versand an eine alte Liste. Prüfen Sie Ihre Spam-Rate in den Google Postmaster Tools und senden Sie langsamer, bis sie wieder unter 0,1 % liegt.

**Was bedeutet der Outlook-Statuscode 5.7.1?**
In Microsoft 365 bedeutet ein 5.7.1 von Outlook meist, dass eine Exchange-Richtlinie oder eine Gruppenbeschränkung die Zustellung gesperrt hat. Bei Privatkonten von Outlook.com und Hotmail enthält er oft den Code S3150. Das bedeutet, dass Microsoft Ihre sendende IP auf seine Sperrliste für Privatkonten gesetzt hat. Sehen Sie S3150, wenden Sie sich an den Betreiber Ihres sendenden Servers und nennen Sie ihm den Link zur Fehlerbehebung aus dem Bounce.

**Was bedeutet "550 5.7.1 outbound relay not allowed"?**
Dieser Fehler bedeutet, dass eine sendende Anwendung E-Mails über einen SMTP-Server senden wollte, ohne sich gültig zu authentifizieren. Mailserver leiten für nicht authentifizierte Absender nichts weiter, damit Spammer nicht über sie senden können. Zur Lösung richten Sie Ihre Anwendung so ein, dass sie sich mit gültigem Benutzernamen und Passwort über eine TLS-Verbindung auf Port 587 anmeldet.

Bewahren Sie den vollständigen Bounce auf, egal was die Ursache ist. Das IT-Team des Empfängers oder Ihr E-Mail-Anbieter fragt als Erstes danach.

Sind die meisten Ihrer Bounces 550 5.1.1 statt 5.7.1, liegt das Problem bei der Liste. Dann lohnt es sich, sie vor dem nächsten Versand [mit Giggal.ai zu prüfen](/email-list-cleaning) (auf Englisch).
